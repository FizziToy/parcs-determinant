# Перевірка та оптимізація PARCS determinant

Перевірено гілку `refactor-parallel`, початковий коміт `e35ca13`. До змін усі
11 тестів пройшли. `main`, старі `results.csv`, `outputs/` і шаблон DOCX збережено.
Push не виконувався.

## Математика

Модульний метод Гауса коректний над полем простого модуля. Перестановки рядків
змінюють знак; відсутність опорного елемента означає нульовий залишок саме за
цим модулем, а не обов'язково нульовий цілий визначник. Окремий тест перевіряє
цю відмінність. Ненульовий опорний елемент обертається через `pow(a, p-2, p)`.

Межа Адамара обчислюється точно цілими числами: квадрат межі дорівнює добутку
сум квадратів елементів рядків. Умова `M*M > 4*bound_squared` дає `M > 2|det A|`.
CRT із симетричним представленням однозначно відновлює знак і ціле значення.
Зупинка не залежить від випадкового збігу кількох залишків. Ця умова збережена.
`det_mod` і `crt_signed` очікують прості модулі; робочий шлях отримує їх лише
через `required_primes`. Вхідна матриця перевіряється перед розрахунком.

## Виявлені причини

1. Генератор відхиляв 512 через обмеження 400; дозволено 512.
2. Складність становить O(k n³), а не лише O(n³). У локальних матриць seed=2026
   кількість модулів дорівнює 26, 56 і 120 для n=128, 256 і 512.
   Орієнтовний обсяг роботи зростає у 17 та 295 разів відносно 128.
   Це оцінка складності, а не виміряний час.
3. Внутрішній Python-цикл виконував повторні індексації матриці та модульне
   множення для кожного елемента. Саме його вартість домінує на щільних матрицях.
4. У попередній версії послідовна частина запускалася на master. У версії від
   19 листопада 2026 року вона виконується одним віддаленим worker; master
   не виконує математичних обчислень у жодному режимі.
5. RPC передає всю матрицю кожному активному воркеру в кожному повторенні.
   Серіалізація входить у паралельний час, але передача не усуває кубічну роботу.

## Зміни ядра та контракту

Python-варіант кешує опорний рядок і оновлює хвости через list comprehension;
пропуск нульових множників збережено. Не додається обов'язкова залежність.

NumPy-варіант виконує ті самі операції над `int64`, використовуючи зовнішній
добуток і повторно використовуваний робочий буфер. Множники беруться для
додавання: `c = -a_ik / pivot (mod p)`. Усі елементи й множники належать
[0, p-1]; найбільше проміжне значення становить `p*(p-1)`. Перевірка цієї межі
відносно `2**63-1` виключає переповнення. Модулі близько 10^9 безпечні.
Великі вхідні цілі спочатку зводяться за модулем у Python, а вже потім
перетворюються на int64. Для завеликих модулів використовується Python.
`numpy.linalg.det`, округлення і float не використовуються.

Master, Worker, Map (`mymap`), Reduce (`myreduce`), метод `det_mod_batch` та
основні поля JSON I/O збережено. `solver.py` заново зібраний із чотирьох модулів.
Збірка явно записує LF, щоб отримувати однакові SHA256 у Windows і Linux.
18 листопада після локальних замірів змінено лише закінчення рядків згенерованого файла;
тотожність нормалізованих байтів і обидва хеші записано у
`experiments/build_portability.json`. Математичне ядро залишилося тим самим.
Таймер використовує `perf_counter`, якщо він доступний; у Python 2 залишено
сумісний `time.time`. Reduce додатково відхиляє нецілі та неканонічні залишки.

## Розподіл ролей після уточнення 19 листопада

Master читає конфігурацію, надсилає RPC, маршрутизує дані, вимірює час,
порівнює повернуті відповіді та записує Output. Worker 1 виконує
`prepare_problem`: генерацію/перевірку матриці, межу Адамара та вибір модулів.
Map виконується на 1–4 workers. Після Map Worker 1 виконує `reduce_determinant`,
перевіряє залишки та відновлює визначник CRT. Локального fallback на master немає.

Поля `sequential_*` тепер означають базовий запуск на одному віддаленому worker
з передачею матриці, Map і віддаленим Reduce. `parallel_*` вимірює той самий шлях
на p workers. S = T1_remote/Tp_remote; E = S/p. Генерація та вибір модулів
відбуваються один раз на worker поза таймером. NumPy потрібен лише на workers.
Додані поля `execution_model` і `timing_baseline` не дозволяють аналізатору
змішати цю методику зі старою базою на master. План нової серії:
`experiments/workers_only_20261119`. Нових вимірювань цієї архітектури ще немає.
Локальні заміри від 18 листопада характеризують лише незмінене математичне ядро.

## Чи можна розподіляти частини матриці

Можна реалізувати окремий розподілений Гаус над кожним простим модулем:
розмістити рядки блоками, спільно обирати pivot, узгоджувати перестановки,
передавати опорний рядок і синхронізувати оновлення. Для кожного модуля
потрібно близько n послідовних кроків обміну. Для невеликого кластера PARCS
із 26–120 незалежними модулями це збільшує кількість RPC і ускладнює код.
Ефективність такого варіанта без реалізації та вимірювань не підтверджена.

Незалежне обчислення визначників рядкових блоків із подальшим множенням
не є коректним алгоритмом: блоки зазвичай прямокутні. Навіть для квадратних
діагональних блоків добуток не дорівнює визначнику загальної матриці:
для [[1,2],[3,4]] результат -2, а добуток діагональних елементів 4.
Формула через доповнення Шура вимагає оберненості опорного блока та обчислення
зв'язаного доповнення; за окремими модулями блок може бути сингулярним.
Тому поточний коректний розподіл простих модулів збережено.

## Фактичні локальні дані

Windows, CPython 3.12.14, NumPy 2.3.5. Три повторення на розмір, seed=2026.
Початкове ядро завантажено безпосередньо з коміту `e35ca13`.

| n | Початкове Python с | Оптимізоване Python с | NumPy с | Прискорення ядра NumPy |
|---|---:|---:|---:|---:|
|128|0.094249|0.089647|0.007448|12.66|
|256|0.889925|0.807422|0.037356|23.82|
|512|7.641094|6.720102|0.261521|29.22|

Це медіани одного модульного визначника з копіюванням/перетворенням даних.
Вони не є часом повного визначника або хмарним прискоренням за воркерами.

Повні точні локальні розрахунки з CRT виконано тричі для кожного розміру.
Медіани: 128 — 0.170284 с, 256 — 2.402478 с, 512 — 30.100691 с.
У кожному розмірі всі три цілі результати однакові та збігаються за додатковим
простим 1000000009 з Python-ядром, яке не використовувало цей модуль у CRT.
Повна точність алгоритму спирається на межу Адамара, а не на додаткову перевірку.

Python 2 і Python 3 можуть створювати різні матриці через відмінності
`random.randint` навіть за однакового seed. Тому локальний визначник не
порівнюється з історичним хмарним лише за парою size/seed. Генератор збережено
для сумісності; у кожній серії треба фіксувати версію Python і діапазон чисел.

## Перевірки та обмеження

Додано незалежний метод Барейса в тестах, контроль переповнення int64,
довільно великі цілі, малі поля, перестановки, сингулярність за модулем,
випадок 512×512 з відомим від'ємним визначником, збереження вхідної матриці,
відсутність NumPy, перевірку залишків та збір результатів із перевіркою SHA256.
Тести HTTP використовують локальні відповіді і не є запуском PARCS.
Підсумкова перевірка: 28 тестів із NumPy — OK; без NumPy 25 — OK і 3 — skipped.
Окремий тест забороняє всі математичні функції поза контекстом worker;
інший підтверджує відсутність локального fallback при помилці Worker Reduce.
Компіляція `solver.py`, модулів, інструментів та тестів пройшла успішно.

Нові хмарні експерименти не запускалися: доступ є лише у браузерному Cloud Shell
користувача. Підготовлено 12 конфігурацій та CSV зі статусом `not_run` і порожніми
числовими клітинками. Старі результати відокремлені. Вимірювання з надлінійним
прискоренням не трактуються як підтверджена властивість алгоритму.

Старі скрипти розгортання перевірено, але наявний кластер не змінювався.
У master-startup.sh є жорстко задана підмережа 10.128.0.0/24; для нового
розгортання її треба звірити з VPC. Зона, характеристики ВМ, версії Python/NumPy
і digest образу мають бути зафіксовані перед новою серією. Поле RAM старого
PARCS є константою в його коді, тому для звіту слід брати реальні дані GCP.
